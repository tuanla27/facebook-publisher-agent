# Approval Service

`service.mjs` contains the approval rules and `postgres-repository.mjs`
provides the transactional PostgreSQL implementation. The HTTP server is a
boundary only; it requires an injected `authenticate(request)` function and
CSRF protection. It will not start with anonymous or header-only authentication.

The review UI is available through:

- `GET /reviews/<opaque-review-link>`: image preview, exact selected content, Fanpage name, warnings, and three actions.
- `POST /reviews/<opaque-review-link>/decision`: CSRF-protected approve, request changes, or reject action.

The "Yêu cầu sửa" action requires a short feedback note so the next version
has an actionable change request.

When a review contains claims without a public source, approval also requires
a reviewer-attestation code. The code is generated for one reviewer, one Page,
one post version, one selected variant, and explicit claim scopes. The reviewer
must enter the code and an exact confirmation before approval; a missing,
expired, reused, or wrong-scope code keeps the post from being approved.

Inject `publishApproved(post_job_id)` when the approval service is connected to
the publisher. It receives only the server-side job ID after an approved
decision and returns a sanitized result containing the published URL.

Expected actor shape:

```js
{
  authenticated: true,
  actor_id: "reviewer-123",
  tenant_id: "tenant-1",
  role: "reviewer",
  institutional_role: "faculty"
}
```

`institutional_role` is required only when the approved version contains
institutional-attested claims. It must be supplied by the authenticated identity
adapter, not by chat text or a client form, and must match the attestation's
opaque actor ID and scope.

## POC Admin Key (Phase 1)

The single-owner pilot uses one admin key. The key is generated by
`openssl rand -hex 32` or `npm run admin:key-hash`; only its SHA-256 hash is
stored in `.env` as `ADMIN_KEY_HASH`. The raw key is never committed or pasted
into chat.

The admin enters the key via the chat dialog (`AskQuestion`) or the bootstrap
script:

```bash
npm run bootstrap:admin
```

The script prompts for the key interactively, verifies it against
`ADMIN_KEY_HASH`, and writes a 0600 local state file with `role: "admin"` and
`institutional_role: "admin"`. The state file never stores the raw key.

An admin actor can attest institutional claims (including footer links) within
the `official_program_information` scope without a separate reviewer-attestation
code. Self-identifying as admin in chat is never sufficient.

Phase 2 will add key expiry, atomic consumption, SSO, and separate issuer keys.

## Reviewer Attestation Code (Phase 2 extension)

The controlled extension uses a separate scoped code when a reviewer confirms
that a claim marked `needs_verification` was checked. Generate it with the
approval attestation-code adapter after the profile reaches human review with
only source-verification blockers. For the single-host demo, the admin proves
issuance authority by entering the admin key interactively; only its SHA-256
hash is stored in local configuration. The generated record stores only the
reviewer-code hash and binds the code to:

- the post, version, selected variant, and Page;
- the authenticated reviewer;
- the allowed claim scopes;
- a short expiry and one-time consumption.

The approval stores the code reference, reviewer confirmation, scopes, and
consumed timestamp. This records delegated responsibility; it does not make
the code itself evidence that the claim is true. Footer links and claims
outside the granted scopes still need normal sources (unless covered by an
admin institutional attestation).

The service derives content and asset hashes from the stored version. Clients
cannot submit their own hashes, Page ID, reviewer identity, or tenant ID.
Connect this service to the real identity provider, CSRF-protected browser
session, and a migration runner before exposing it outside a private network.
